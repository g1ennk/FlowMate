## 1. Backend (Spring Boot 4) 심층 리뷰

### 1.1 잘된 점

**1) JWT 단일 파싱 + 만료/서명/role 동시 검증**
SSE `/api/timer/sse` 엔드포인트는 쿼리 파라미터로 토큰을 받아야 하는 EventSource 제약을 고려해, 컨트롤러 단에서 `jwtProvider.parseToken(token)` 한 번에 서명·만료·role을 검증합니다 (`timer/controller/TimerController.java:32-48`). 다중 파싱 사이의 만료 race를 원천 차단하는 의도된 설계.

**2) 멀티 디바이스 RTR (Refresh Token Rotation)**
기존 RT를 revoke하고 신규 발급하되, 탈취 의심(stolen reuse) 시 사용자의 모든 활성 RT를 무효화하는 흐름이 명확합니다 (`auth/service/AuthService.java:134-161`). `RefreshToken.isStolenReuse()` (`auth/domain/RefreshToken.java:56`)와 `findAllActiveByUserId()` 쿼리가 정책을 코드 레벨에서 강제합니다. 멀티 디바이스 동시 로그인 허용 + 침해 시 전면 격리.

**3) N+1 회피의 명시적 구현**
Todo reorder는 여러 ID를 단일 `findAllByIdInAndUserId`로 조회 후 `Map<String, Todo>` 매핑으로 선형 시간 처리 (`todo/service/TodoService.java:159-188`). 주석으로 의도를 기록했고 실제 구현도 일치합니다.

**4) SSE 브로드캐스트 원자성**
fire-and-forget 방식 + 예외 흡수로 SSE 전송 실패가 트랜잭션을 롤백시키지 않도록 합니다 (`timer/service/SseEmitterRegistry.java:62-77`). 클라이언트는 `GET /api/timer/state`로 보정 가능. 주석에 의도가 명확히 기록되어 있어 향후 변경 시 실수 방지.

**5) OSIV off + JPA Auditing**
`open-in-view: false` (`application.yml:5`)로 뷰 단 lazy loading 위험을 차단했고, `@EnableJpaAuditing`으로 `createdAt/updatedAt` 자동화. JPA 안티패턴을 의식한 설계.

**6) 쿠키 보안 환경별 분기**
`COOKIE_SECURE` 환경변수로 HTTPS 환경만 Secure 플래그 활성화 (`auth/service/AuthService.java:187-196`). HttpOnly + SameSite=Lax + path=/api/auth로 RT 스코프를 최소화.

**7) 데드락 → catch-retry 전환의 기록 있는 의사결정**
처음 gap lock으로 데드락을 경험했고 `@Lock` 제거 + `DataIntegrityViolationException` catch-retry로 전환 (`timer/repository/TimerStateRepository.java:16-19`, `timer/service/TimerService.java:50-62`). `docs/wiki/timer-deadlock.md`에 부하 테스트 검증(163,205건 0 실패)까지 기록.

**8) 광역 예외 매핑**
`GlobalExceptionHandler` 20여 개 예외를 명시적으로 매핑 (`common/web/GlobalExceptionHandler.java:36-165`). 사용자 메시지 노출 위험도 의식해 500은 "서버 내부 오류"로 추상화 (라인 154). Record 기반 `ApiError`로 직렬화 안정.

**9) Flyway 점진적 진화 + 무결성 검증**
V1(스키마)→V2(인증)→V3(타이머)→V4(복습 스케줄)→V5(timestamp 정합 부채 청산)로 의도가 분리되어 있고, prod는 `validate-on-migrate: true`. 마이그레이션이 도메인 변경의 일등 시민으로 다뤄집니다.

**10) OAuthProviderRegistry — Open/Closed 원칙**
생성자에서 `List<OAuthProvider>`를 자동 주입받아 Map으로 변환 (`auth/oauth/OAuthProviderRegistry.java:23-26`). 새 OAuth 제공자 추가 시 `@Component`만 구현하면 자동 등록되는 확장 모델.

### 1.2 문제점 (심각도별)

#### HIGH

**[BE-H1] JWT 만료 신호의 단일 401**
`JwtAuthFilter.java:60`는 `JwtException` 발생 시 SecurityContext만 비워두므로 클라이언트는 만료/위조/누락을 구분할 수 없습니다. 클라이언트(`http.ts:51-114`)는 401만 보고 refresh 시도하는데, 위조 토큰에 대해서도 동일 처리가 일어나 불필요한 refresh 호출을 유발합니다.
- 영향: 클라이언트 refresh 분기 추측 부담 + 위조 시 BE/AS 호출 낭비
- 권장: `TokenExpiredException`을 별도 정의하고 `{ code: "TOKEN_EXPIRED" }` 본문 또는 419 차등 응답

**[BE-H2] SSE 쿼리파라미터 토큰의 노출 표면**
SSE는 EventSource 제약상 헤더 사용 불가라 토큰을 `?token=` 으로 전송 (`TimerController.java:32-48`). Nginx access log, CDN, 모바일 OS HTTP 캐시에 잔존 가능. Access JWT TTL이 15분으로 짧지만, SSE 연결 TTL은 1시간이라 재활용 창이 더 깁니다.
- 영향: 로그 유출 시 15분간 임의 위조 가능
- 권장: SSE 전용 단기 (예: 60초 발급, 5분 유효) 토큰 엔드포인트 신설. 또는 `Sec-WebSocket-Protocol` 트릭 활용

**[BE-H3] Actuator 환경별 분기 부재**
`SecurityConfig.java:39-46`는 `/actuator/**` 무조건 permitAll. Prod는 Nginx에서 `/actuator/health`만 화이트리스트(`prod/nginx.conf:104-119`)이지만, **앱 레벨에서 한 번 더 막는 defense-in-depth가 없음**. Nginx 설정 실수 한 줄이면 prometheus/metrics/env/configprops 등이 노출됩니다.
- 영향: 운영 변경 실수 시 즉시 정보 노출
- 권장: `@Profile("local|dev")` 분기 + prod에서는 명시 endpoint 화이트리스트

**[BE-H4] Todo 상태 전이 규칙 강제 부재**
복습 스케줄 API는 `isDone()` 체크만 합니다 (`todo/service/TodoService.java:194`). 엔티티 레벨 transition 강제가 없어 동시 요청(완료↔미완료↔복습)에서 일관성 깨질 수 있음. version 필드(optimistic lock)도 없음.
- 영향: 비즈니스 규칙 위반 가능, 복습 체인 오염
- 권장: Todo 엔티티에 `@Version` 추가 + `validateStateTransition()` 메서드

**[BE-H5] 멱등성 키 의존성 — 클라이언트 책임 과중**
`SessionService.java:38-62`는 `clientSessionId`로 멱등성을 보장하지만 형식 검증 없이 신뢰합니다. 클라이언트가 매번 새 UUID 생성하면 멱등성 무의미.
- 영향: 의도하지 않은 중복 세션
- 권장: UUID 형식 정규식 검증 추가, 가능하면 `Idempotency-Key` 헤더 표준화

#### MEDIUM

**[BE-M1] `CurrentUserResolver`가 인증 누락 시 500 던짐**
`common/util/CurrentUserResolver.java:10-16`에서 `IllegalStateException`을 throw → `GlobalExceptionHandler`에서 500 매핑. SecurityConfig 정합성이 깨지면 사용자에게 500이 노출됩니다. 보안 경계가 깨졌을 때의 신호로는 401이 더 정확.
- 권장: `AuthenticationFailedException` 또는 별도 예외 → 401 매핑

**[BE-M2] Dirty checking UPDATE의 명시성**
`TodoService.updateTodo` (`102-143`)는 setter들로 dirty checking에 의존. 조건부 필드 변경 로직이 복잡해지면 NULL 갱신 사고 가능.
- 권장: 명시적 `save()` 호출 또는 메서드 책임 분리

**[BE-M3] Token hash 유틸 중복 가능성**
`AuthService.sha256()` private static (`auth/service/AuthService.java:198-206`). 다른 시크릿에 같은 패턴 필요 시 중복 발생.
- 권장: `common/crypto/CryptoUtils` 추출

**[BE-M4] SSE 초기 send 실패 신호 부재**
`SseEmitterRegistry.java:51-57` — `emitter.send("connected")` 실패 시 로그만 남고 클라이언트에는 HTTP 200이 이미 발송됨. 클라이언트의 `onopen`이 호출되어 연결됐다고 오해.
- 권장: 별도 ping/handshake 폴링 또는 SSE retry 명시

**[BE-M5] ReviewRound 체인 제목 cascade의 모호성**
`TodoService.resolveBaseTitle()` (`191-259`) — round 1 제목 변경 시 round 2+ cascade가 코드만 보면 불명확.
- 권장: 통합 테스트 추가 + 의사결정 wiki 페이지화

#### LOW

**[BE-L1] 복습 간격 상수 하드코딩** (`TodoService.java:30-31`)
`REVIEW_INTERVALS = {1,2,4,8,16,32}`, `MAX_REVIEW_ROUND = 6` 하드코딩.
- 권장: `application.yml`로 설정화

**[BE-L2] 매직 숫자 in 마이그레이션**
`V1__init.sql`의 `mini_day INT NOT NULL DEFAULT 0`, `session_order` 등에 CHECK 제약 없음.
- 권장: 범위 CHECK 추가

**[BE-L3] HTTP 메서드 단위 권한 미세화 부족** (`SecurityConfig.java:38-50`)
`/api/timer/state/**`가 메서드 무관 hasRole.
- 권장: 향후 DELETE 추가 시 분기 고려

**[BE-L4] 통합 테스트 비중 부족**
27개 테스트 대부분이 service Mockito 단위. SSE broadcast/RTR 엣지 테스트 약함.
- 권장: §5에서 Testcontainers 도입 권고와 함께 다룸

**[BE-L5] 마이그레이션 롤백 스크립트 없음**
V*.sql만 있고 U*.sql 없음. Flyway Community는 undo 미지원이라 한계지만, 수동 롤백 SQL을 wiki에 두는 것 권장.

## 2. Frontend (React 19 + Vite 7) 심층 리뷰

### 2.1 잘된 점

**1) HTTP 클라이언트 — Singleton refresh + Zod 검증**
`api/http.ts:48-114`에서 401 동시 발생 시 `refreshPromise` 전역 변수로 한 번만 호출. 세션 타입 변경(member→guest) 감지해 재시도 방지 (79-82). Zod로 에러 응답 정규화, Bearer 자동 주입. 클라이언트 인증 흐름의 모범 사례.

**2) 인증 부팅의 저지연**
`store/authStore.ts:27-64`의 `init()` — authMode 힌트로 분기해 API 호출 최소화. 게스트 토큰이 있으면 0 호출로 초기화, member 힌트만 refresh 시도. Access token은 메모리만 사용, 게스트 토큰만 localStorage — 보안 모델이 명료.

**3) 타이머 version 단조 제어**
`features/timer/timerStore.ts:198-225`의 `applyRemoteState()` — 로컬 version > server version이면 무시. todoId별 `seenVersions` Map으로 중복 적용 방지. `getIsApplyingRemote()` 플래그로 SSE↔로컬 경합 감지.

**4) SSE 재연결 + 토큰 갱신 통합**
`useSseTimerSync.ts:68-110` — `sseRefreshing` 플래그로 중복 호출 방지, 토큰 만료 판단 후만 refresh. Principal(guest/member:userId) 변경 시 기존 연결을 닫고 신규 생성. push 큐 + 지수 백오프(2^attempt).

**5) Optimistic update + 세션 집계 보호**
`features/todos/hooks.ts:50-87` — `onMutate` 낙관 업데이트 + `onSuccess`에서 `Math.max(current.sessionCount, next.sessionCount)`로 다중 세션 동시 생성 시 감소 덮어쓰기 방지.

**[INF-H3] 배포 워크플로 분기 버그** (`deploy-prod-backend.yml:23-61`)

- 영향: 잘못된 이미지 배포 위험, 워크플로의 의도와 실제 동작이 분리됨
- 권장: deploy를 `needs: build-and-push`로 묶고 dispatch에서 version만 추가 입력

**[INF-H4] CloudFront `--paths "/*"` 전체 무효화** (`deploy-prod-frontend.yml:64-68`)
배포마다 캐시 미스, CF 비용 증가.
- 권장: 변경 파일만 추출해 path 지정 (해시 파일명 활용)

**[INF-H5] 시크릿 평문 주입** (`infra/prod/docker-compose.yml:53,135` 등)
`JWT_SECRET`, `GEMINI_API_KEY`, `POSTGRES_PASSWORD`, `MYSQL_PASSWORD`가 `.env` 의존. `docker inspect` 시 노출.
- 권장: AWS Secrets Manager + Docker secrets 또는 SOPS-encrypted file

**[INF-H6] MySQL slow query log 외부 마운트 없음** (`prod/docker-compose.yml:22-25`)
`--slow-query-log=ON --log-output=FILE`이지만 mount 없음. 컨테이너 재시작 시 로그 손실.
- 권장: `./logs/mysql:/var/log/mysql:rw` 볼륨 추가

**[INF-H7] Alloy 메트릭 카디널리티 무필터** (`config.alloy:23-49`)

## 6. Cross-cutting Issues — 영역을 가로지르는 패턴

리뷰 과정에서 다수 영역에 걸쳐 반복되는 패턴 6가지가 식별됩니다.

### 6.1 보안 표면 — JWT/세션의 신호 부족

- BE-H1 (JWT 만료 단일 401), BE-H2 (SSE 토큰 쿼리 노출), AI-H3 (서비스 토큰 부재), FE-M1 (403 처리)
- **공통 원인**: 토큰의 *상태 다양성*을 단일 401로 평탄화. 클라이언트가 분기 추측을 강요받음.
- **공통 해결**: `{ code: "TOKEN_EXPIRED" | "TOKEN_INVALID" | "TOKEN_REVOKED" }` 본문 표준화. AI 서비스용 service-to-service 토큰 분리. FE는 403을 별도 분기.

### 6.2 시크릿/구성 관리

- INF-H5 (시크릿 평문 .env), AI-L2 (env 검증 약함), BE 환경별 actuator 분기 부재(BE-H3)
- **공통 원인**: 설정·시크릿이 환경변수 하나로 평탄화되고 부팅 시점 검증이 약함.
- **공통 해결**: AWS Secrets Manager 또는 SOPS-encrypted YAML로 이관. 부팅 시 zod-style schema 검증 (NestJS는 `@nestjs/config` ValidationSchema, Spring은 `@ConfigurationProperties` + `@Validated`).

### 6.3 관찰성 — 메트릭은 있는데 알람·SLO가 없음

- INF: Alloy로 LGTM 스택 구축 완료 but alerting rule 없음
- BE: Prometheus 메트릭 있으나 도메인 메트릭(예: 복습 스케줄 성공률) 빈약
- AI: Gemini latency/error 메트릭 부재
- **공통 원인**: "수집"은 했으나 "신호화"는 안 됨.
- **공통 해결**: SLO 정의 (p95 latency, error rate) → Grafana Cloud alerting rule → Slack 채널.

### 6.4 테스트 게이트 누락

- BE-L4 (통합 테스트 비중), FE-L2 (커버리지 26%), AI-L1 (테스트 거의 없음), DOC-H1 (CI 게이트 없음), DOC-H5 (커버리지 측정 없음)
- **공통 원인**: 테스트 자산은 있지만 *자동 게이트*가 없어 "있어도 되고 없어도 되는" 상태.
- **공통 해결**: PR 시 모든 영역 (BE/FE/AI) 테스트 자동 실행 + 커버리지 60% 게이트.

### 6.5 단일 실패점

- INF-H1 (단일 EC2), INF-H2 (다운타임), INF-M4 (PG 백업), 단일 ECR/CF/Region
- **공통 원인**: 인프라가 운영 환경 *진화 단계 1*에 머묾.
- **공통 해결**: 데이터 백업·복구를 먼저(즉시 실행 가능), 그 다음 인스턴스 이중화, 마지막에 multi-region.

### 6.6 의사결정 보존 vs 코드의 갭

- 잘된 영역: `auth-evolution.md`, `timer-deadlock.md` — 진화 + 트레이드오프 + 검증
- 부족 영역: SSE 선택 근거, AI 서비스 NestJS 선택, FE Zustand+RQ 조합, 클러스터 스택 선택
- **공통 해결**: docs/adr/ 도입 + PR 템플릿에 "Decision recorded?" 체크박스

## 9. 결론 및 권고

### 9.1 종합 결론

FlowMate는 **개인 사이드 프로젝트 기준 매우 높은 수준의 엔지니어링 성숙도**를 보입니다. RTR·SSE·Flyway·LGTM 스택·Strategy 패턴·docs/wiki 의사결정 로그까지 — 흔히 회사 인프라에서만 보는 수준의 패턴이 모두 갖춰져 있습니다. 무엇보다 **트레이드오프와 진화 단계를 docs/wiki에 기록하는 습관**이 가장 큰 자산입니다(`auth-evolution.md`, `timer-deadlock.md`).

### 9.2 핵심 권고

1. **테스트 게이트를 가장 먼저 잠그세요.** 작성된 테스트가 CI에서 강제 실행되지 않으면 시간이 갈수록 휘발됩니다. P0 #1·#10이 30분~1시간 투자로 최대 ROI입니다.
2. **시크릿/보안 표면 일괄 점검 — 1주 캠페인으로**. Prompt Injection, JWT 만료 신호, actuator 분기, .env 평문 — 개별로는 작지만 묶어서 처리하면 1~2일 안에 끝납니다.
3. **운영 관찰성을 "수집"에서 "신호"로 격상**. Alloy/Grafana Cloud는 이미 들어가 있으므로, alerting rule + SLO 정의만 추가하면 RED 메트릭 기반 운영 체계가 단번에 완성됩니다.
4. **단일 EC2 위험은 백업·복구부터 — 다중화는 그 다음**. 즉시 실행 가능한 PG/MySQL pg_dump 백업을 P1으로 잡고, 다중화는 트래픽 늘어나는 시점에 재검토해도 충분합니다.
5. **포트폴리오 차원에선 ADR + README 개선이 큰 ROI**. 이미 수준 높은 작업물을 "보이게 만드는" 작업은 2~3시간 투자로 임팩트 큽니다.

### 9.3 마지막 한 줄

> 잘 만들어졌습니다. 이제 **잘 만들었음을 자동으로 증명**하고(테스트·SLO), **잘못 만들어지는 것을 막는 게이트**(보안·시크릿)를 까는 단계입니다.
